# 이미지 프롬프트 생성 Agent 개선 계획

- 작성일: 2026-08-12
- 대상: `opod-admin`
- 현재 이미지 모델: Nano Banana Pro
- 다음 이미지 모델 후보: FLUX + ComfyUI
- 상태: 조사와 계획 완료, 구현 전

게시물 생성 파이프라인의 Agent별 책임과 공통 프롬프트 원칙은
`2026-08-12-post-generation-agent-role-redesign.md`를 따른다. 이 문서의
장면별 사례와 실험 규칙은 조사·검증 자료이며, 특정 캐릭터나 한 번의 실패에
귀속된 지시를 공통 프롬프트로 승격하는 근거가 아니다.

## 1. 이 계획의 목표

조사한 이미지와 프롬프트 자료를 이용해 `이미지 프롬프트 생성 Agent`를 개선한다.

최종 목표는 다음과 같다.

> 생성 Agent가 실제 사람이 그 자리에서 찍은 사진처럼 보이는 이미지를 만들 수 있는 프롬프트를 작성하게 한다.

평가 Agent는 이 목표를 달성했는지 검사하는 도구다. 조사 자료의 주된 사용처는 평가 기준이 아니라 프롬프트 생성 Agent다.

## 2. 조사 자료를 어디에 쓸 것인가

조사한 자료는 네 가지 용도로 사용한다.

### 2.1 좋은 프롬프트의 작성 순서 찾기

Hugging Face, arca.live, Civitai, Reddit 등에서 이미지와 프롬프트가 함께 공개된 사례를 모은다.

각 프롬프트를 다음 부분으로 나눠 본다.

1. 인물이나 물건
2. 행동과 상황
3. 장소
4. 누가 어떤 기기로 찍었는지
5. 카메라 위치와 화면 구성
6. 빛이 어디서 오는지
7. 피부, 옷, 유리, 금속 같은 재질 표현
8. 일상 사진다운 작은 불완전함
9. 참조 이미지에 맡길 것과 글로 지시할 것

좋은 결과에서 반복되는 순서를 찾아 Nano Banana Pro용 생성 규칙으로 만든다.

### 2.2 OPOD 장면별 좋은 예시 만들기

커뮤니티 프롬프트를 그대로 복사하지 않는다. OPOD가 자주 만드는 장면에 맞춰 다시 작성한다.

먼저 다음 장면별 예시를 만든다.

- 친구가 찍어 준 일상 사진
- 고정된 휴대폰과 타이머로 찍은 사진
- 거울 셀피
- 얼굴이 나오지 않는 상반신 또는 몸 일부 사진
- 카페와 식당
- 거리와 산책
- 집 안의 일상
- 음식과 물건만 나온 사진
- 밤과 어두운 실내
- 여러 장이 한 게시물로 이어지는 사진

각 장면에는 다음 세 가지를 같이 보관한다.

- 좋은 프롬프트 예시
- 나쁜 프롬프트 예시
- 왜 차이가 나는지에 대한 짧은 설명

이 예시는 프롬프트 생성 Agent의 지시문을 개선할 때 참고하고, 필요한 소수의 예시는 Agent에게 직접 보여준다.

### 2.3 잘못된 습관 제거하기

좋은 사례만 보지 않는다. 커뮤니티에서 자주 사용하지만 실제 사진 느낌을 떨어뜨리는 표현도 찾는다.

우선 확인할 대상은 다음과 같다.

- `masterpiece`, `best quality`, `8k`, `ultra detailed` 같은 품질 단어 묶음
- 장면과 맞지 않는 `cinematic`, `studio lighting`, 과한 얕은 심도
- 스마트폰 사진과 전문 DSLR 사진 표현을 동시에 쓰는 경우
- 모든 인물에게 모공, 주근깨, 잔털을 강제로 넣는 경우
- 아무 장면에나 노이즈, JPEG 깨짐, 기울어진 구도를 넣는 경우
- 같은 내용을 긍정문과 금지문으로 계속 반복하는 긴 프롬프트
- 참조 이미지가 이미 보존할 외모를 글로 다시 자세히 묘사하는 경우

이 내용은 생성 Agent가 피해야 할 규칙과 프롬프트 작성 후 자체 점검 항목으로 사용한다.

### 2.4 개선 전후를 비교할 시험 자료 만들기

조사 자료에서 배운 내용을 제품에 바로 넣지 않는다. OPOD용 장면 시험 세트를 만들고 현재 Agent와 개선 Agent의 결과를 비교한다.

예를 들어 다음처럼 비교한다.

- 현재 긴 프롬프트 대 상황 중심의 짧은 프롬프트
- 품질 단어가 있는 프롬프트 대 없는 프롬프트
- 참조 이미지 역할이 불분명한 프롬프트 대 역할을 나눈 프롬프트
- `professional photo` 중심 프롬프트 대 실제 휴대폰 촬영 상황 중심 프롬프트
- 피부 세부를 많이 적은 프롬프트 대 빛과 촬영 거리만 정확히 적은 프롬프트

평가 Agent와 실제 사람 평가를 이용해 어느 쪽이 더 자연스러운 결과를 만드는지 확인한다.

### Hugging Face 자료 등급

- A급: 이미지, 원본 프롬프트, 모델 이름과 버전, 참조 이미지, 사용 조건을 확인할 수 있다.
- B급: 이미지와 프롬프트는 있지만 일부 생성 정보가 없다. 작성 방식 분석에 사용한다.
- C급: 프롬프트만 있거나 출처가 불분명하다. 아이디어로만 참고한다.

좋아요가 많거나 `photorealistic`이라는 이름이 붙었다고 좋은 사례로 판단하지 않는다. OPOD 장면과 가까운지, 실제 사진처럼 보이는지, 다시 비교할 수 있는지를 확인한다.

## 4. 현재 프롬프트 생성 Agent의 문제

현재 코드를 확인한 결과 장점과 문제는 다음과 같다.

### 잘 되어 있는 부분

- Nano Banana, FLUX, Stable Diffusion을 구분해서 다른 작성 규칙을 준다.
- 장면에 보일 내용과 촬영 방법을 나눠 입력한다.
- 인물이 보이지 않는 사진에는 외모 설명을 넣지 않는다.
- 여러 사진의 인물, 의상, 장소와 빛을 이어서 작성하려고 한다.
- Nano Banana 편집에서 인물 참조 사진의 자세와 배경을 그대로 복사하지 않도록 지시한다.

### 개선할 부분

#### 규칙이 너무 길고 특정 실패 사례에 치우쳐 있다

현재 Nano Banana 규칙에는 얼굴 가리기, 상반신 자르기, 휴대폰 위치 같은 매우 구체적인 규칙이 항상 들어간다. 해당 장면에는 도움이 되지만 다른 장면에도 매번 전달된다.

그 결과 중요한 촬영 상황보다 예외 규칙이 더 눈에 띌 수 있다. 공통 규칙과 특정 장면 규칙을 나눠야 한다.

#### 좋은 예시가 없다

Agent는 많은 금지 규칙을 받지만, 좋은 일상 사진 프롬프트가 어떤 모습인지 예시를 받지 않는다.

조사한 자료에서 검증된 예시를 뽑아 모델별로 소수만 제공해야 한다.

#### 참조 이미지 역할을 정확히 알지 못한다

현재 Agent는 참조 이미지가 있다는 사실 때문에 편집 모델을 쓰는지는 알 수 있다. 하지만 그 참조가 다음 중 무엇인지는 입력으로 받지 못한다.

- 인물 정체성 참조
- 장소와 배경 참조
- 의상이나 물건 참조
- 스타일 참조

그래서 장소 사진만 첨부되어도 “같은 사람의 정체성을 유지하라”는 문장을 만들 가능성이 있다. 생성 Agent 입력에 참조 이미지의 역할을 알려줘야 한다.

#### 프롬프트가 왜 그렇게 작성됐는지 추적하기 어렵다

현재는 최종 프롬프트만 저장한다. 어떤 작성 규칙과 예시 버전으로 만들었는지 분명하지 않다.

`builder-v2`, 사용 모델, 참조 종류, 예시 묶음 버전을 기록해야 개선 효과를 비교할 수 있다.

## 5. Nano Banana Pro용 Agent 개선안

현재 사용하는 모델이 Nano Banana Pro이므로 이 모델부터 개선한다.

### 5.1 프롬프트 작성 순서를 고정한다

Agent가 다음 순서로 한 번씩만 작성하게 한다.

1. 참조 이미지의 역할과 유지할 내용
2. 최종 화면에 나올 인물·물건과 행동
3. 장소와 주변 물건의 배치
4. 실제 촬영자와 촬영 기기
5. 카메라 높이, 거리, 방향과 화면 범위
6. 장면에서 실제로 생기는 빛
7. 필요한 재질과 작은 불완전함
8. 꼭 필요한 금지 사항

같은 내용을 여러 문장으로 반복하지 않는다.

### 5.2 공통 규칙과 상황별 규칙을 나눈다

모든 사진에 필요한 공통 규칙은 짧게 유지한다.

- 자연스러운 영어 문장으로 쓴다.
- 하나의 실제 촬영 상황으로 설명한다.
- 카메라, 빛, 인물 행동이 서로 가능해야 한다.
- 품질 단어 묶음과 가중치 문법을 쓰지 않는다.
- 입력에 없는 외모와 신체 특징을 만들지 않는다.
- 최종 화면에 보이는 내용만 구체적으로 쓴다.

상황별 규칙은 필요한 사진에만 넣는다.

- 거울 셀피일 때만 휴대폰과 반사 규칙 사용
- 얼굴 비노출 사진일 때만 자르기와 가림 규칙 사용
- 타이머 사진일 때만 고정된 휴대폰과 빈손 규칙 사용
- 여러 사진일 때만 의상·장소·빛 고정 규칙 사용
- 장소 참조가 있을 때만 건축·재질·배치 유지 규칙 사용

### 5.3 참조 이미지 역할을 입력에 추가한다

각 사진마다 최소한 다음 정보를 프롬프트 생성 Agent에 전달한다.

- 인물 참조가 있는지
- 장소 참조가 있는지
- 각 참조의 짧은 설명
- 어떤 정보만 가져오고 어떤 정보는 무시할지

인물 참조가 있을 때만 정체성 유지 문장을 사용한다. 장소 참조만 있으면 인물 관련 문장을 쓰지 않고 구조, 재질, 색, 고정 물건만 유지하게 한다.

처음에는 기존 데이터에 이미 있는 참조 설명을 전달한다. 새로운 데이터베이스 구조는 만들지 않는다.

### 5.4 검증된 좋은 예시를 넣는다

Agent에게 모든 커뮤니티 프롬프트를 넣지 않는다. Nano Banana Pro 실험을 통과한 3~5개의 짧은 예시만 사용한다.

예시는 다음 차이를 보여줘야 한다.

- 친구가 찍은 사진과 셀프 타이머 사진
- 인물 참조와 장소 참조의 다른 사용법
- 실제 휴대폰 사진과 과하게 연출된 광고 사진의 차이
- 한 장과 여러 장 게시물의 차이

예시가 특정 인물, 성별, 장소나 의상을 기본값으로 만들지 않도록 다양하게 구성한다.

### 5.5 작성 후 스스로 확인하게 한다

최종 JSON을 만들기 전에 Agent가 내부적으로 다음을 확인하도록 한다.

- 촬영자가 실제로 그 위치에서 찍을 수 있는가?
- 보이는 손의 수와 행동이 맞는가?
- 참조 이미지에서 가져오면 안 되는 배경이나 자세를 복사하지 않았는가?
- 같은 내용을 반복하지 않았는가?
- 화면에 없는 내용을 자세히 묘사하지 않았는가?
- 광고나 영화 사진처럼 만드는 불필요한 표현이 있는가?
- 여러 사진에서 인물과 장소가 갑자기 변하지 않는가?

이 점검 결과는 별도 긴 설명으로 출력하지 않고 최종 프롬프트를 고치는 데만 사용한다.

## 6. 조사 자료를 실제 규칙으로 바꾸는 절차

한 자료를 발견했을 때 다음 순서로 처리한다.

### 1단계: 자료 기록

- 원문 주소
- 작성 날짜
- 이미지 모델과 버전
- 원본 프롬프트
- 참조 이미지 사용 여부
- 확인 가능한 생성 설정
- 사용 조건과 라이선스

### 2단계: 프롬프트 분해

어떤 문장이 인물, 행동, 촬영, 구도, 빛, 재질, 불완전함을 담당하는지 표시한다.

### 3단계: 이미지 결과와 연결

좋았던 부분과 AI처럼 보인 부분을 따로 기록한다. 프롬프트에 있는 표현이 실제 결과에 어떤 영향을 줬는지 추정한다.

### 4단계: OPOD용 가설 작성

예:

> `professional portrait`를 빼고 실제 촬영자와 휴대폰 위치를 구체적으로 쓰면 일상 사진 느낌이 좋아질 것이다.

### 5단계: A/B 비교

현재 Agent와 변경 Agent가 같은 기획과 참조 이미지로 결과를 만든다. 한 번에 한 가지 규칙만 바꾼다.

### 6단계: 채택 또는 폐기

평가 Agent 점수뿐 아니라 사람 블라인드 평가가 좋아졌을 때만 생성 규칙에 넣는다. 실패한 방법도 연구 기록에 남긴다.

## 7. 시험할 장면과 비교 방법

### 첫 시험 세트

Nano Banana Pro용으로 30~50개의 고정 장면을 만든다.

- 인물 있음/없음
- 인물 참조만 있음
- 장소 참조만 있음
- 인물과 장소 참조가 모두 있음
- 친구 촬영, 타이머, 거울 셀피
- 얼굴 노출, 일부 가림, 얼굴 없음
- 실내/실외, 낮/밤
- 한 장/여러 장

실제 사용 동의가 있는 참조 이미지만 사용한다.

### 비교 방법

- 같은 기획과 참조 이미지를 사용한다.
- 가능한 경우 같은 seed 또는 같은 수의 반복 생성을 사용한다.
- 현재 Agent와 개선 Agent의 결과를 섞어서 보여준다.
- 평가자는 어느 쪽이 새 Agent인지 모르게 한다.
- 프롬프트 자체와 생성 이미지 결과를 따로 평가한다.

### 꼭 볼 결과

- 사람이 실제 사진처럼 느끼는 비율
- 장면과 프롬프트가 맞는 비율
- 인물 정체성 유지
- 의상과 장소의 연속성
- 손, 반사, 휴대폰, 글자 오류
- 과한 피부 보정, HDR, 채도와 광고 느낌
- 재생성 횟수와 최종 후보 선택률

처음부터 성공 기준 숫자를 확정하지 않는다. 현재 Agent의 수준을 먼저 측정한 다음 개선 목표를 정한다.

## 8. 평가 Agent는 어떻게 사용할 것인가

평가 Agent는 조사 자료를 직접 학습시키는 주체가 아니다. 다음 역할을 맡는다.

### 프롬프트 평가 Agent

- 생성 Agent가 장면 기획을 빠뜨리지 않았는지 확인한다.
- 촬영자, 카메라, 손, 거울이 물리적으로 가능한지 본다.
- Nano Banana Pro 작성 규칙을 지켰는지 본다.
- 참조 이미지의 역할을 올바르게 사용했는지 본다.
- 불필요하게 길거나 같은 내용을 반복하는지 본다.

### 이미지 평가 Agent

- 생성된 결과가 실제 사진처럼 보이는지 본다.
- 빛, 재질, 손, 반사, 신체, 물건이 자연스러운지 본다.
- 인물, 의상, 장소가 참조 이미지와 이어지는지 본다.
- 예쁘지만 광고나 3D 렌더처럼 보이는 결과를 따로 표시한다.

### 사람 평가

평가 Agent가 놓치는 전체적인 어색함을 확인한다. 최종 채택 여부는 사람 블라인드 평가를 가장 중요한 기준으로 삼는다.

평가 기준 개선은 생성 Agent 실험을 정확히 측정하는 데 필요한 범위에서 진행한다. 평가 기준 자체가 이번 조사 자료의 주된 결과물은 아니다.

## 9. 구현 순서

### 1단계: 조사 자료를 정리하고 첫 시험 세트 만들기

- Hugging Face와 커뮤니티 자료를 장면별로 분류한다.
- 좋은 예시, 나쁜 예시, 배운 규칙을 정리한다.
- OPOD용 고정 장면 30~50개를 만든다.
- 현재 `builder-v1`의 Nano Banana Pro 결과를 기준점으로 기록한다.

이 단계에서는 서비스 동작을 바꾸지 않는다.

### 2단계: 참조 이미지 역할을 생성 Agent에 전달하기

- 현재 데이터에 있는 인물 참조와 장소 참조를 나눠 전달한다.
- 참조 이미지의 짧은 설명도 전달한다.
- 인물 참조가 있을 때만 정체성 보존 문장을 사용한다.
- 장소 참조만 있는 사진에 인물 지시가 들어가지 않도록 테스트한다.

### 3단계: Nano Banana Pro 생성 규칙 정리

- 공통 규칙을 짧게 만든다.
- 얼굴 가림, 거울, 타이머, 여러 사진 등의 규칙은 필요한 장면에서만 적용한다.
- 검증된 좋은 예시 3~5개를 추가한다.
- 불필요한 품질 단어와 반복을 제거한다.
- 새 버전을 `builder-v2`로 기록한다.

### 4단계: 개선 전후 생성 비교

- 고정 장면으로 `builder-v1`과 `builder-v2` 프롬프트를 만든다.
- Nano Banana Pro로 같은 수의 이미지를 생성한다.
- 평가 Agent와 사람 블라인드 평가를 함께 실행한다.
- 좋아진 항목과 나빠진 항목을 장면별로 기록한다.

### 5단계: 효과가 확인된 규칙만 적용

- 모든 장면에서 좋아진 공통 규칙은 유지한다.
- 특정 장면에서만 좋아진 규칙은 상황별 규칙으로 둔다.
- 효과가 없거나 부작용이 있는 규칙은 제거한다.
- 결과를 `docs/prompt-research-log.md`에 남긴다.

### 6단계: FLUX·ComfyUI용으로 확장

- 같은 장면 시험 세트를 사용한다.
- Nano Banana Pro의 문장을 그대로 복사하지 않는다.
- FLUX에 맞는 자연어 프롬프트와 ComfyUI 설정을 따로 만든다.
- 모델, LoRA, sampler, scheduler, steps, guidance, 크기, denoise, 노드 버전을 함께 기록한다.
- Nano Banana Pro와 FLUX의 결과를 한 점수로 섞지 않는다.

## 10. 예상 코드와 문서 변경 위치

### 프롬프트 생성 Agent

- `prompts/image-prompt-builder.ts`
  - Nano Banana Pro 공통 규칙 정리
  - 상황별 규칙 적용
  - 검증된 좋은 예시 추가
  - 참조 이미지 역할별 작성법 추가
- `src/worker/image-prompt-builder.ts`
  - 참조 이미지 역할과 설명을 입력으로 전달
  - 생성 규칙 버전 기록
- `src/worker/draft-worker.service.ts`
  - 기존 인물·장소 참조 정보를 빌더 입력에 연결
- `src/worker/image-prompt-builder.spec.ts`
  - 인물 참조, 장소 참조, 참조 없음의 동작 보호
  - 상황별 규칙이 필요한 사진에만 들어가는지 확인

### 평가와 기록

- `prompts/prompt-evaluator.ts`
  - 참조 역할, 반복, 과한 연출 표현을 평가하도록 필요한 범위만 보완
- `prompts/image-evaluator.ts`
  - 실제 사진 느낌과 광고·렌더 느낌을 분리
- `docs/prompt-research-log.md`
  - 자료 출처, 가설, 변경, 전후 결과와 채택 여부 기록

새 라이브러리나 범용 프롬프트 관리 시스템은 만들지 않는다. 기존 모델별 분기와 기존 연구 로그를 사용한다.

## 11. 꼭 필요한 테스트

- 인물 참조가 있으면 인물 정체성 유지 지시가 들어가는가?
- 장소 참조만 있으면 인물 정체성 지시가 들어가지 않는가?
- 참조가 없으면 편집 모델용 문장을 쓰지 않는가?
- 거울 셀피 규칙이 일반 거리 사진에 들어가지 않는가?
- 얼굴 비노출 규칙이 얼굴 노출 사진에 들어가지 않는가?
- 여러 장 연속성 규칙이 여러 장에만 적용되는가?
- 생성된 프롬프트 수와 사진 순서가 기획과 일치하는가?
- 기존에 보호하던 얼굴, 손, 휴대폰, 의상과 장소 규칙이 깨지지 않는가?
- 평가가 실패해도 이미지 생성 작업 자체를 막지 않는가?

프롬프트 전체 문장을 그대로 비교하는 테스트는 만들지 않는다. 실제로 보호해야 하는 작성 원칙과 결과 형식만 테스트한다.

구현 후에는 다음을 실행한다.

- `npm run lint`
- `npm run test`
- `npm run build`
- 관련 평가 API까지 바뀌면 `npm run test:e2e`

## 12. 이번 계획에 포함하지 않는 것

- 커뮤니티 프롬프트를 검증 없이 그대로 복사하는 것
- Hugging Face 전체 자료를 실행 중인 Agent에 검색시켜 넣는 큰 검색 시스템
- 좋아요 수만으로 좋은 프롬프트를 선정하는 것
- AI 탐지기를 속이는 방향으로 프롬프트를 최적화하는 것
- AI 생성 표시, SynthID, C2PA 같은 출처 정보를 제거하는 것
- 평가 결과에 따라 자동으로 프롬프트를 고치고 다시 생성하는 것
- 새 데이터베이스나 새 라이브러리를 먼저 추가하는 것

## 13. 이미 결정된 내용

- 조사 자료의 주된 사용처는 이미지 프롬프트 생성 Agent 개선이다.
- 평가 Agent는 개선 효과를 측정하고 실패 원인을 찾는다.
- 현재는 Nano Banana Pro를 먼저 개선한다.
- 이후 FLUX·ComfyUI를 별도 작성 규칙으로 지원한다.
- Hugging Face의 이미지와 프롬프트 묶음을 가장 먼저 조사한다.
- arca.live, Civitai, Reddit, Discord에서 실제 사용자 경험과 실패 사례를 보완한다.
- 커뮤니티 팁은 OPOD 장면 A/B 평가를 통과해야 제품 규칙이 된다.
- 현재 모델별 분기를 활용하고 큰 새 구조는 만들지 않는다.

## 15. 구현 전 경계

이 문서는 구현 계획이다. 코드, 테스트, 데이터베이스는 아직 변경하지 않았다.

구현을 승인받으면 먼저 다음 범위만 진행한다.

1. 조사 자료를 OPOD 장면별 좋은 예시·나쁜 예시·작성 규칙으로 정리
2. Nano Banana Pro 고정 장면 시험 세트 작성
3. 참조 이미지 역할을 생성 Agent에 전달
4. Nano Banana Pro 공통 규칙과 상황별 규칙 정리
5. `builder-v1`과 `builder-v2` 비교

FLUX·ComfyUI 적용은 Nano Banana Pro 개선 효과를 확인한 뒤 별도 단계로 진행한다.
