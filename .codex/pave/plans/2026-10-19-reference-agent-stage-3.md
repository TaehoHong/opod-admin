# 레퍼런스 기반 게시물 생성 Agent — 3단계 설계

- 날짜: 2026-10-19
- 상태: 후속 사용자 승인으로 3단계 runtime과 저장·조회 계약을 구현했다. 실제 DB·공급자 검증과 최종 인수는 보류하며 현재 구현 범위는 [전체 개발 계획](2026-10-19-reference-agent-development-plan.md)을 따른다.
- 선행 설계: [2단계](2026-10-19-reference-agent-stage-2.md)
- 범위: 확정한 입력으로 이미지를 생성하고 결과를 저장한다. 별도 LLM 기획·검수는 추가하지 않는다.

## 확정 아키텍처

사용자 결정(user-confirmed): 이미지 생성 추상 → 이미지 모델 설정에 따른 구현체 선택 → 해당 구현체에서 모델에 맞게 요청 조립.

```text
생성 Worker
    ↓ 공통 생성 요청
이미지 생성 인터페이스
    ↓ 이번 작업에 고정된 provider·model 설정으로 구현체 선택
모델별 구현체
    ↓ 요청 조립 및 실행
외부 이미지 생성 API
    ↓ 공통 진행 상태·결과로 변환
생성 Worker → 검증·영구 저장
```

| 계층 | 책임 |
| --- | --- |
| 생성 Worker | 작업 실행·상태·재시도·결과 저장. 모델별 전송 형식을 모른다. |
| 구현체 선택부 | 작업에 저장된 provider·model 설정으로 구현체를 고른다. |
| 이미지 생성 인터페이스 | 공통 제출·상태 조회·결과 계약을 정의한다. |
| 모델별 구현체 | 모델별 요청 조립·입력 제한 검사·호출·응답 정규화를 담당한다. |

현재 ImageGenerationProvider 및 ImageGenerationRequest 소유자를 확장한다. 별도 평행 인터페이스를 만들지 않는다. Worker에 모델별 payload 분기를 추가하지 않는다. 같은 provider의 모델들이 서로 다른 규약을 가지면 구현체 내부의 모델별 요청 빌더로 처리할 수 있다.

## 공통 입력

- prompt
- negativePrompt
- references: 원본과 캐릭터 이미지의 식별자·역할·고정된 순서 및 접근 정보
- generationOptions: 작업에 고정된 비율·해상도 등
- 작업 식별자와 멱등성 키

구현체 선택에 사용하는 모델 설정은 2단계에 고정한 것과 일치해야 한다. 현재 설정이 변경됐다는 이유로 진행 중인 작업의 모델을 바꾸지 않는다. 자격증명은 기존 설정 소유자가 공급하며 초안·일반 로그에 저장하지 않는다.

원본은 구도·포즈 참조, 캐릭터 비주얼은 정체성 참조다. 기존 provider 공통 계약의 composition/identity 역할 등으로 명시적으로 매핑한다. provider가 역할 필드를 직접 받지 않더라도 이미지 순서와 프롬프트의 대응은 보존한다.

## 처리 흐름

### 1. 컷별 작업 준비 — 코드

2단계에서 확정한 프롬프트·negative·원본·캐릭터 참조·순서·설정을 사용한다. 별도 재선택이나 프롬프트 재작성을 하지 않는다. 각 컷은 독립 작업으로 관리해 실패한 컷만 다시 처리할 수 있게 한다.

### 2. 구현체 선택 및 제출 — 코드 + 이미지 생성 모델

선택부가 저장된 설정에 해당하는 구현체를 고른다. 기존 미디어 접근 기능을 사용해 유효한 입력을 준비하고 구현체가 모델 요청 형식에 맞게 조립한다. 서명 URL이 필요한 경우 제출 직전에 발급한다. 지원하지 않는 설정이나 참조 수 초과 시 중단하며 다른 모델로 자동 변경하거나 필수 참조를 잘라내지 않는다.

negative 처리 역시 구현체 책임이다.
- 별도 필드 지원: 해당 필드로 전달.
- 별도 필드 미지원: 본문에 제외 지시로 합쳐 전달.
- 빈 문자열: 불필요한 제외 절을 만들지 않음.
- 원본 prompt/negativePrompt와 실제 전송 본문을 구분해 기록.
- 본문 병합과 전용 negative 필드의 효과가 같다고 보장하지 않음.

현재 SpicyAPI Seedream 경로는 nonempty negative를 거부하므로 본문 병합은 필요한 구현 변경이다. Worker가 이를 우회하지 않고 해당 구현체가 처리한다. 변환은 한 번만 수행해 중복 삽입·조용한 누락을 방지한다.

### 3. 상태 추적 — 코드

외부 작업 ID를 제출 직후 저장하고 기존 provider의 submit/poll 계약으로 진행을 추적한다. 단순 지연·일시적 조회 실패는 같은 작업 조회를 이어가며 새 요청으로 바꾸지 않는다. 서버 재시작 후에도 저장된 작업 ID로 재개한다.

확정된 작업 실패 후 허용되는 재시도는 기존 재시도 정책을 따른다. 외부 제출 성공 여부가 불확실한 구간은 provider의 멱등성·조회 지원 범위 내에서 복구하며, 일반 인터페이스만으로 정확히 한 번 실행을 보장한다고 주장하지 않는다. 완료된 다른 컷은 재생성하지 않는다.

### 4. 결과 검증·영구 저장 — 코드

기존 generated-image-validation과 생성 미디어 저장 소유자를 재사용한다.

| 검사 | 목적 |
| --- | --- |
| 결과 이미지 존재 | 빈 응답을 성공 처리하지 않음 |
| 이미지 디코딩 가능 | 오류 페이지·손상 파일 차단 |
| 형식·크기·해상도 | 확정된 출력 조건 확인 |

검증한 결과를 기존 생성 이미지 S3 경로에 저장하고 해당 컷과 연결한다. 외부 임시 URL만으로 저장 완료 처리하지 않는다. 실제 요청·provider 작업 ID·모델·원본 연결·결과 미디어·오류 정보를 추적하며 비용은 provider가 반환하는 경우 기록한다.

이 검증은 파일 검증이며 정체성·구도·자연스러움의 시각적 품질 판정이 아니다. 별도 LLM 검수나 자동 프롬프트 수정 루프는 이번 흐름에 포함하지 않는다.

### 5. 캡션 단계로 전달 — 코드

요청한 모든 컷이 현재 프롬프트/생성 리비전에 맞는 결과로 영구 저장됐을 때만 다음 단계로 진행한다. 결과 완료 순서와 무관하게 초안의 컷 순서를 유지한다. 실패·저장 실패·진행 중 컷이 남으면 불완전한 묶음으로 캡션을 시작하지 않는다. 이전 입력 리비전의 늦은 결과가 현재 컷을 덮어쓰지 않도록 기존 리비전 검증을 확장한다.

## 완료 기준

초안의 모든 컷에 저장된 생성 이미지가 연결되고 실제 요청과 원본 참조의 추적 정보가 남는다. 이미지 생성 완료는 게시 완료가 아니며 게시된 사용 이력은 게시 단계에서 반영한다.

## 구현 검증 기준

- 저장된 provider·model 설정으로 올바른 구현체를 선택한다.
- Worker가 모델별 전송 필드를 직접 조립하지 않는다.
- 원본/캐릭터 순서와 prompt/negative 조건이 실제 요청에 반영된다.
- negative 전용 필드와 본문 병합, 빈 negative를 각각 확인한다.
- 일시적 조회 실패·재시작에서 기존 작업 ID를 재사용한다.
- 한 컷 실패 시 완료된 다른 컷은 재생성하지 않는다.
- 손상 결과·저장 실패를 완료로 처리하지 않는다.
- 모든 컷의 현재 리비전 결과 저장 후에만 캡션으로 넘어간다.
- 후속 사용자 승인으로 snapshot 기반 generation job 생성·실행·집계를 연결했다. 실제 공급자/DB 검증은 보류하며 최종 전체 검사 상태는 전체 개발 계획을 따른다.
