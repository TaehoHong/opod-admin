# OPOD 게시글 생성 Skill·Agent 개선 브리프 — 한소이 한강 게시물

> 작성일: 2026-08-26  
> 근거: 한소이 한강 산책 게시물 제작·검수·직접 게시 과정에서 발생한 사용자 지시, 평가, 승인과 오류 대응 기록  
> 목적: `opod-content-production` Skill, 게시글 생성 Agent, 이미지 검수 및 관리자 직접 게시 흐름 개선

## 1. 작업 결과

- 캐릭터: 한소이
- 콘셉트: 한소이가 직접 촬영한 한강 산책 기록
- 핵심 조건: 한소이는 촬영자이므로 사진에 출연하지 않음
- 게시 형식: 이미지 5장의 피드 게시물
- 최종 캡션: `📸`
- 해시태그: 없음
- 게시 대상: 외부 SNS가 아닌 OPOD 내부 피드
- 최종 게시물 ID: `01a03b8e-aa99-75f0-a8de-712df93b6484`

## 2. 사용자가 명시한 제작 지시

### 2.1 콘셉트와 시점

- 사진은 한소이 본인이 촬영한 설정이다.
- 촬영자인 한소이는 사진에 등장하지 않는다.
- 관찰자 시점의 자연스러운 스냅사진이어야 한다.
- 멀리서 찍은 듯한 구도와 적절한 카메라 기법을 사용한다.

### 2.2 필요한 장면

- 실제 한강 산책로 풍경
- 러닝하는 사람들의 뒷모습
- 강아지와 노는 사람들
- 서로 이야기하며 달리는 뒤쪽의 두 사람
- 오른쪽 러너는 러닝 조끼 착용
- 러너들의 머리 모양은 서로 다르게 표현

### 2.3 장소와 구도

- 실제 한강 산책로의 도로 구조와 주변 환경을 참고한다.
- 일반적인 공원이나 임의로 만든 도로처럼 보이면 안 된다.
- 풀숲 안에서 촬영한 위치도 구도상 타당하면 허용한다.
- 다만 풀이 지나치게 높거나 화면을 과도하게 가리면 안 된다.
- 원경과 전경의 인물을 정확히 구분해야 한다.

## 3. 사용자의 부정적 평가

다음 특성이 이미지의 인위성을 높인다고 평가했다.

- 사람들이 지나치게 정돈되거나 연출된 모습
- 인물들의 헤어스타일이 모두 비슷한 모습
- 실제 한강과 다른 산책로 폭, 포장과 배치
- 촬영자의 위치가 납득되지 않는 구도
- 풀이 지나치게 높아 카메라가 풀숲에 갇힌 듯한 화면
- `뒤의 두 명`을 앞쪽 인물로 잘못 해석하는 공간 관계 오류
- 특정 사진만 수정하면서 전체 이미지의 페르소나 일관성을 재검토하지 않는 방식
- 사용자가 요청하지 않은 게시 연동 방식이나 선택지를 제안하는 행동
- 근거를 확인하기 전에 오류 원인을 추정해 단정하는 행동

## 4. 사용자의 긍정적 승인 기준

- 실제 장소에서 우연히 촬영한 듯 자연스럽다.
- 촬영 거리와 카메라 위치가 현실적으로 설명된다.
- 인물들이 카메라를 의식하지 않고 행동한다.
- 대화, 달리기, 강아지와 놀기 같은 상호작용이 자연스럽다.
- 전경·중경·배경 인물의 역할이 명확하다.
- 사람마다 머리 모양과 복장이 달라 군집이 복제된 것처럼 보이지 않는다.
- 사진 전체의 구도와 필터가 한소이의 관찰자형 페르소나와 맞는다.
- 사진 5장이 서로 다른 장면이면서 하나의 산책 기록처럼 연결된다.
- 캡션은 길게 설명하지 않아도 된다. 이번 작업에서는 `📸`만으로 승인됐다.

## 5. 피드백 해석 시 주의할 점

### 5.1 `풀숲에서 찍었냐`의 최종 의미

처음에는 촬영 위치가 부자연스럽다는 지적이었지만, 이후 사용자는 구도상 필요하다면 풀숲에 들어가 촬영해도 괜찮다고 정정했다.

최종 규칙은 다음과 같다.

> 풀숲 촬영 자체를 금지하지 않는다. 촬영 위치가 구도를 통해 납득되어야 하며, 풀 높이와 화면 점유율을 조절한다.

### 5.2 `뒤에 두 명`의 의미

단순히 인물 두 명을 추가하는 요청이 아니다.

- 대상은 원경 또는 배경의 두 사람이다.
- 앞쪽 인물은 변경 대상이 아니다.
- 두 사람은 서로 대화하며 이동해야 한다.
- 오른쪽 인물에게 러닝 조끼를 적용한다.

Agent는 수량뿐 아니라 깊이, 좌우 위치, 행동 관계까지 필드로 분해해야 한다.

## 6. Skill에 추가할 규칙

### 6.1 콘텐츠 계약 확장

아이디어 선택 시 다음 필드를 잠근다.

- 촬영자
- 촬영자의 화면 출연 여부
- 카메라와 피사체 사이의 거리
- 카메라가 위치한 장소
- 전경·중경·배경별 인물
- 인물 사이의 상호작용
- 좌우 위치별 의상 특징
- 장소의 실제 구조적 특징

### 6.2 레퍼런스 조사 강화

- 소셜 레퍼런스와 실제 장소 레퍼런스를 구분해 수집한다.
- 소셜 레퍼런스에서는 구도, 거리감과 인물 행동을 추출한다.
- 장소 레퍼런스에서는 도로 폭, 포장, 차선, 난간, 식생과 강의 위치를 확인한다.
- 생성 전 실제 장소와 모순되는 요소를 목록화한다.
- 특정 게시물을 복제하지 않고 여러 레퍼런스의 특징을 조합한다.

### 6.3 이미지 생성 프롬프트 강화

장면마다 다음 정보를 명시한다.

- 카메라 위치와 높이
- 예상 촬영 거리
- 원경·중경·전경 배치
- 피사체가 카메라를 의식하는지 여부
- 인물별 행동과 상호작용
- 인물별 헤어스타일과 복장 차이
- 장소에서 반드시 보여야 할 구조
- 화면을 과도하게 가리면 안 되는 요소

### 6.4 검수 절차 강화

검수는 두 단계로 수행한다.

1. 개별 사진 검수
   - 장소 현실성
   - 카메라 위치의 개연성
   - 인물 깊이와 좌우 위치
   - 인물 다양성
   - 복장과 행동 일치
   - AI 특유의 반복과 대칭
2. 전체 캐러셀 검수
   - 한소이 페르소나 일관성
   - 색감과 필터 일관성
   - 촬영 거리의 자연스러운 변주
   - 장면 순서와 산책 서사
   - 이미지 사이 인물·환경의 불필요한 반복

한 장을 수정했더라도 최종 승인 전에는 전체 사진을 다시 검토한다.

### 6.5 수정 요청 처리

- `4번만 다시`는 4번 이미지 외의 결과를 잠근다.
- 수정 요청을 대상, 깊이, 좌우, 행동, 외형과 의상 필드로 분해한다.
- 사용자가 언급하지 않은 필드는 유지한다.
- 수정 결과를 보여주기 전에 요청한 대상이 정확히 바뀌었는지 확인한다.
- `뒤`, `오른쪽`, `두 명` 같은 공간 지시어를 독립된 제약 조건으로 다룬다.

### 6.6 캡션 규칙

- 짧은 캡션도 정상적인 최종 결과로 인정한다.
- 승인된 `📸`은 한소이의 승인 사례로 저장하되 모든 게시물의 기본값으로 일반화하지 않는다.
- 이미지가 충분히 말하고 있으면 불필요한 상황 설명을 덧붙이지 않는다.
- 해시태그는 필요하지 않으면 생성하지 않는다.

### 6.7 게시 규칙

- 기본 게시 대상은 OPOD 내부 피드다.
- 외부 Instagram 게시를 임의로 제안하거나 실행하지 않는다.
- MCP가 없어도 로그인된 브라우저 세션과 관리자 UI를 사용할 수 있다.
- 아이디와 비밀번호를 Skill, 저장소 또는 대화에 저장하지 않는다.
- 게시글 목록의 `직접 게시` 기능을 우선 사용한다.
- 이미지 순서, 캐릭터, 캡션과 해시태그를 게시 직전에 검증한다.
- 완료 후 게시물 ID와 관리자 링크를 반환한다.

## 7. Agent 행동 개선

### 7.1 피드백 기억 구조

각 피드백을 다음 구조로 저장한다.

```text
scope: global | character | post | shot
target: 적용 대상
instruction: 사용자의 원문 지시
resolved_rule: 최종적으로 확정된 규칙
status: active | superseded | example_only
evidence: 승인 또는 수정 요청
```

예시:

```text
scope: character
target: hansoi.visual.pov
resolved_rule: 한소이는 관찰자형 촬영자이며 필요한 경우 화면에 출연하지 않는다.
status: active
```

```text
scope: shot
target: runners.background.right
resolved_rule: 뒤쪽 오른쪽 러너는 러닝 조끼를 착용한다.
status: active
```

```text
scope: character
target: hansoi.caption.example
resolved_rule: 📸
status: example_only
```

### 7.2 오류 대응 원칙

- 먼저 사용자 화면의 오류 원문을 그대로 수집한다.
- 브라우저, OPOD API와 외부 저장소 오류를 구분한다.
- 서버 로그에 오류가 없다면 없다고 명확히 말한다.
- 추정 원인과 확인된 원인을 구분한다.
- 배포 직후에는 기존 탭을 새로고침해 새 번들, CSP와 설정을 적용한다.
- 실패한 요청이 부분적으로 처리됐는지 확인한 뒤 재시도한다.
- 게시 성공은 목록의 상태와 게시물 ID로 확인한다.

이번 작업에서는 처음 CORS 문제로 추정했지만, 실제 확인 결과는 기존 탭에 남아 있던 이전 CSP였다. 서버 설정 반영 후 페이지를 새로고침하자 게시에 성공했다. 이후에는 추정보다 원문과 응답 헤더를 먼저 확인해야 한다.

## 8. 회귀 평가 시나리오

Skill 또는 Agent 변경 후 다음 시나리오를 반드시 통과해야 한다.

1. `4번만 다시` 요청 시 다른 네 장이 변경되지 않는다.
2. `뒤의 두 명` 요청 시 전경 인물이 아니라 배경 인물을 수정한다.
3. 오른쪽 러너에게만 러닝 조끼가 적용된다.
4. 여러 인물의 머리 모양이 반복되지 않는다.
5. 실제 한강 레퍼런스와 산책로 구조가 일치한다.
6. 풀숲 촬영 구도는 유지하되 풀 높이가 화면을 지배하지 않는다.
7. 수정 후 다섯 장 전체의 구도와 필터를 다시 점검한다.
8. 캡션 `📸`, 해시태그 없음 상태를 그대로 게시한다.
9. 다섯 장의 업로드 순서를 보존한다.
10. 게시 실패 시 오류 원문을 먼저 보여주고 근거 없는 원인을 단정하지 않는다.
11. 배포 변경 후 새로고침하고 다시 시도한다.
12. 게시 성공 후 게시물 ID와 관리자 링크를 반환한다.

## 9. 개선 우선순위

1. 부분 수정 시 잠금 필드와 공간 관계 보존
2. 실제 장소 구조 검증
3. 사람들의 외형·행동 다양성 검수
4. 한 장 수정 후 전체 캐러셀 재검수
5. 브라우저 기반 직접 게시 절차 정식 지원
6. 오류 원문 중심의 진단과 배포 후 새로고침
7. 승인 사례와 일반 규칙을 분리하는 메모리 구조
