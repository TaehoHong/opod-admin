# 프롬프트 연구 로그 — 게시물 생성 Agent

게시물 생성 Agent의 프롬프트(`prompts/`)와 평가 루브릭 변경을 실험 기록
방식으로 남긴다. 포트폴리오 정리의 원자료이므로 결과와 실사례를 구체적으로
적는다.

개선 과정 전체의 연대기는
[post-creation-agent-architecture-v3.md](./post-creation-agent-architecture-v3.md) §19에
있다. 이 문서는 그중 **프롬프트·루브릭 실험**만 소유한다.

## 기록 규칙

- 프롬프트·루브릭 변경마다 버전을 올리고 아래 템플릿으로 엔트리를 추가한다.
- 버전 체계: 대상별 독립 버저닝 — `planner-vN`, `builder-vN`, `eval-rubric-vN`.
- 결과는 가능한 한 정량으로: 평가 차원별 점수 변화, 검수 거절률, 컷 재생성
  횟수, 캡션 수정률. 정량이 없으면 대표 실사례(draft ID + 발췌)를 남긴다.
- 실패한 실험도 기록한다 — 롤백한 변경과 그 이유가 포트폴리오에서 더 중요하다.

### 엔트리 템플릿

```markdown
## <대상>-v<N> — <한 줄 제목> (YYYY-MM-DD)

- 상태: 적용 중 | 롤백 | 관찰 중
- 가설: 어떤 문제를 어떤 변경으로 개선할 수 있다고 봤는지
- 변경: 추가/수정한 프롬프트 규칙 (핵심 문장 인용 또는 diff 요약)
- 결과: 평가 점수·휴먼 시그널 변화, 대표 사례 (before/after)
- 판정: 유지 / 부분 유지 / 롤백 — 근거
- 다음: 이 결과가 시사하는 후속 실험
```

  장소·비주얼 프로필을 입력으로 캡션·해시태그·컷 구성(기본 2컷, 최대 3컷)을

  - 캡션 말투가 캐릭터 개별 페르소나와 무관하게 균질해지는 경향
  - AI틱한 상투 문형(정형화된 감탄·마무리 멘트) 발생
  - 정량 측정 수단 부재 → 평가 Agent(eval-rubric-v1)로 계측 예정

## eval-rubric-v1 — 평가 루브릭 초판 (2026-08-07)

- 상태: 적용 중 (2026-08-10 재구성, `plan-prompt-evaluation-agent.md` 참조)
- 구성: 기획 평가 8차원 (persona_fit, voice_tone_fit, ai_tell_free,
  memory_continuity, location_coherence, shot_composition, reference_usage,
  caption_quality) + 프롬프트 평가 6차원 (scene_capture_separation,
  physical_consistency, model_family_rules, plan_fidelity,
  reference_alignment, cross_shot_consistency).
- 설계 결정 기록:
  - voice_tone_fit은 페르소나 텍스트만으로 판정 불가 → 최근 게시 캡션을
    평가 입력에 포함해 비교하는 방식 채택
  - ai_tell_free는 AI 티 패턴을 **언어별 패턴 팩**(en, ko, …)으로 분리해
    루브릭 버전과 함께 관리 — 서비스가 글로벌·다국어 타겟임이 확정되며
    한국어 단일 패턴에서 설계 변경(2026-08-07). 영어 팩은 공개 연구 자산
    (Wikipedia AI Cleanup, 과대표현 어휘 목록) 기반, 타 언어는 자체 구축
  - 평가는 비동기 워커로 비차단 실행 (LLM 3연쇄 lease 부담 회피)
  - 프롬프트 평가는 2계층 설계 (`image-prompt-evaluation-agent.md`):
    결정적 결함은 정적 린트로 무비용 검출, LLM은 의미 수준 심사만 담당.
    전 컷 배치 1콜로 컷 간 일관성(cross_shot_consistency)까지 판정.
    정답 신호는 생성 결과(실패율·재생성·후보 선택률)와의 상관으로 계측 —
    차원별 예측력 검증이 루브릭 v2 보정의 근거가 된다.
- 다음: 실제 draft에 대한 점수 분포 확인 → 차원별 변별력 검증,
  휴먼 검수 결과와의 상관으로 루브릭 보정 (v2 후보)

## v3-schema-v2 — structured outputs 문법 호환 수정 (2026-08-13)

- 상태: 적용 중
- 대상: `prompts/post-planner.ts`, `prompts/image-planner.ts`,
  `src/worker/v3-evaluators.ts`의 JSON schema. 시스템 프롬프트 문장과
  계약 의미(`post-plan-v1`, `image-plan-v1`)는 바꾸지 않았다.
- 발단: 개발 서버에서 V3를 켜고 만든 초안의 게시글 기획이 전부 실패했다.
  ```
  structured agent failed (400): Invalid schema for response_format
  'opod_post_plan_v1': In context=(), 'oneOf' is not permitted.
  ```
- 원인: V3 스키마가 표준 JSON Schema로 작성됐지만 OpenAI 호환 structured
  outputs(strict)는 부분집합만 받는다. 2026-08-13 실제 프로바이더(gpt-5.6-terra,
  api.openai.com) 응답으로 확인한 위반 3종:

  | 위반 | 위치 | 프로바이더 응답 |
  |---|---|---|
  | 루트 `oneOf` | post-plan, image-plan | `'oneOf' is not permitted` |
  | `uniqueItems` | image-plan 5곳, evaluator 2곳 | `'uniqueItems' is not permitted` |
  | `type` 없는 `const` | post-plan·image-plan status, evaluator 4곳 | `schema must have a 'type' key` |

  같은 확인에서 **허용**되는 것도 함께 고정했다: 중첩 `anyOf`(널 허용 포함),
  `enum`, string `minLength`/`maxLength`, array `minItems`/`maxItems`,
  integer `minimum`/`maximum`. 루트 `anyOf`도 거부된다(루트는 object여야 함).
- 변경:
  1. 판별 union은 `prompts/strict-schema.ts`의 `rootUnionSchema()`로 루트
     object 한 겹(`result`)에 감싼다. 감싼 사실은 전송 계층
     (`strict-json-agent.ts`)이 응답에서 자동으로 벗기므로 Agent 파서와 저장
     artifact 모양은 그대로다. `isRootUnionSchema()`로 감싼 쪽과 벗기는 쪽이
     어긋날 수 없게 했다.
  2. `const` → `{ type: "string", enum: [값] }`.
  3. `uniqueItems` 제거. 중복 금지는 런타임 파서가 이미 강제한다
     (`stringArray`/`textArray`/`numberArray`의 Set 비교). 즉 계약이 약해진
     것이 아니라 검증 주체가 스키마에서 파서로 옮겨졌다. 대신 모델이 중복을
     내면 400이 아니라 파싱 실패로 나타난다 — 단계 실패 메시지에 `has
     duplicates`가 찍히면 이 경로다.
- 결과: 세 스키마(`opod_post_plan_v1`, `opod_image_plan_v1`,
  `opod_prompt_set_v1`)를 실제 엔드포인트에 직접 보내 전부 SCHEMA ACCEPTED
  확인. 단위 테스트 403개 통과.
- 부수 발견 (더 중요): **capability probe가 가짜 통과를 냈다.** 기존 probe는
  `{ok: true}` 하나짜리 스키마만 확인해서, 정작 배포된 V3 스키마 전부가 400을
  받는 상태에서 "V3 strict JSON schema 지원 확인"을 반환했다. 운영자는 그
  초록불을 보고 V3를 켰고, 실패는 초안 단계에서야 드러났다. probe를 실제
  스키마와 같은 문법(루트 union envelope + 중첩 anyOf + enum + 길이·개수 제한)
  으로 바꾸고, 네트워크 전에 배포된 스키마를 `assertStrictSchemaCompatible()`
  로 먼저 검사하도록 했다.
- 판정: 유지. 계약 버전(`post-plan-v1`/`image-plan-v1`)은 올리지 않는다 —
  전송 인코딩만 바뀌고 Agent가 주고받는 의미와 저장 artifact는 동일하다.
- 회귀 방지: `src/worker/strict-schema.spec.ts`가 정적 스키마 3종과 평가 Agent
  스키마 6종(조립 시점에 캡처)을 같은 규칙으로 검사한다. 프로바이더 문법을
  어기는 스키마는 네트워크 없이 테스트에서 걸린다.
- 다음: 다른 프로바이더(Anthropic·Gemini 호환 경로)를 붙일 때 이 부분집합이
  또 달라진다. 지금은 OpenAI 호환만 가정하므로, 프로바이더가 늘면
  `strict-schema.ts`를 프로바이더별 프로파일로 확장한다.

## image-planner-v2 — 촬영 기하 일관성과 종횡비 범위 (2026-08-13)

- 상태: 관측 중 (재실행 1회 전)
- 대상: `prompts/image-planner.ts` 시스템 프롬프트. 스키마와 계약 버전
  (`image-plan-v1`)은 바꾸지 않았다.
- 발단: 실제 초안의 ImagePlan에서 `capture_plausibility` 3/5, `major` 지적이
  나왔다. 평가자 진단이 정확했다.

  ```
  scene:        "전신거울에 비친 목 아래 전신 … 스마트폰이 얼굴을 완전히 가리고"
  captureSetup: "스마트폰 전면 카메라를 든 인물이 … 미러 셀피를 촬영한다"
  ```

  거울 셀카는 화면이 나를 향하고 **후면** 카메라가 거울을 향한다. 전면
  카메라는 나를 직접 찍으므로 "거울에 비친 전신"이 나올 수 없다. 폰을 뒤집어
  전면 카메라를 거울로 향하게 하면 찍히긴 하지만 화면이 안 보이고 거울에
  폰 화면이 비친다. 즉 scene과 captureSetup이 기하학적으로 양립하지 않는다.
- 가설: 기존 프롬프트에는 "physically plausible … with an ordinary available
  device"라는 일반 문장만 있어, **장치의 광학 방향**까지는 강제되지 않는다.
  scene/captureSetup 분리 규칙도 "무엇을 어디에 쓰는가"만 말하고 "둘이
  성립하는가"는 말하지 않는다. 원칙 한 줄 + 재발 사례(거울) 한 줄을 넣으면
  같은 결함이 줄어든다.
- 변경:
  1. Responsibilities에 촬영 기하 규칙 추가 —
     `captureSetup must be geometrically able to produce scene.` 반사 뷰는
     렌즈가 반사면을 향해야 하므로 셀프 미러샷은 후면 카메라이고 거울에는
     기기 뒷면이 보인다, 전면 카메라는 피사체를 직접 담고 반사 뷰를 만들지
     않는다. 손·기기·팔다리·몸 방향이 한 사람에게 동시에 가능해야 한다.
  2. Scope boundary의 `generation settings`에 `including aspect ratio and
     resolution`을 명시. 같은 산출물이 `captureSetup`에 "세로 4:5"를 적었는데,
     종횡비는 설정이 게시 형식에서 유도한다(`aspectRatioFeed` 등, `324899b`).
     기획이 정할 값이 아니고, crop/framing이라면 애초에 `scene` 소관이다.
- 결과 (2026-08-14, draft `019ffa17…`, artifact `promptVersion: image-planner-v2`,
  imagePlanning revision 1):

  | 컷 | 기획한 촬영 | 결과 |
  |---|---|---|
  | 0 미러 셀카 | `rear camera … aiming the lens squarely at its reflective surface` | **규칙이 겨냥한 결함 재발 없음** |
  | 1 거치 촬영 | `propped upright on the cream shoe cabinet … aimed directly toward her` | 같은 차원에서 **새 유형** 결함 |

  컷 1의 scene은 "그 신발장이 그녀 뒤에 보인다"고 썼다. 카메라를 올려둔 물체는
  카메라 위치, 즉 프레임 밖에 있으므로 배경에 나올 수 없다. 평가자가 major로
  잡았다.

  ```
  capture_plausibility 3/5 · issues_found · 총점 4.818 (= 53/11, 한 차원만 3점)
  ```

  **v1 때와 수치가 동일하다.** 결함의 종류만 바뀌었다.

- 판정: **부분 유지.** 사례(거울)는 해결됐고 원칙 일반화는 미달이다. 규칙을
  "원칙 한 문장 + 재발 사례 한 문장"으로 썼는데, 모델이 사례는 따르고 원칙은
  일반화하지 못했다. "카메라를 지지하는 면·물체는 프레임 밖"은 원칙
  (`captureSetup must be geometrically able to produce scene`)의 직접 귀결인데
  지켜지지 않았다. 롤백하지 않는다 — 되돌리면 거울 결함이 돌아온다.
- 표본 주의: **관측 1건이다.** 거울 결함이 나지 않은 것이 규칙 덕인지 우연인지
  1건으로는 가릴 수 없다. 다만 같은 차원에서 다른 결함이 났다는 사실은
  "`capture_plausibility`가 이 파이프라인의 구조적 약점"이라는, 표본 1건보다
  강한 신호다.
- 부수 관측: 평가자는 두 번 다 정확했다. `docs/post-creation-agent-architecture-v3.md`
  §18.8에 기록한 평가자 사각지대 3건과 대조된다 — `capture_plausibility`는
  작동하고 `scope_compliance`·`ai_tell_free`는 놓친다.
- 다음 후보 (미적용): v3에서 원칙에 귀결을 하나 명시한다 — 촬영자와 카메라를
  지지하는 면·물체는 프레임 밖이며 scene에 등장할 수 없다. 적용 전에 관측을
  더 모아 사례 나열이 아니라 원칙 강화로 가는지 확인한다.
- 방법 주의: **평가자 프롬프트는 이번에 건드리지 않는다.** 같은 산출물에서
  평가자가 놓친 것이 하나 더 있다 — `captureSetup`의 "세로 4:5"는
  `scope_compliance` 소관인데 5/5를 줬다. 측정 대상(기획자)과 측정 도구
  (평가자)를 동시에 바꾸면 점수 변화가 어느 쪽 때문인지 알 수 없다. 기획자
  변경의 효과를 먼저 관측하고, 평가자 보정은 별도 엔트리로 다룬다.
- 관측 방법: 같은 초안에서 ③ 이미지 기획을 재실행하고
  `capture_plausibility` 점수와 `captureSetup`의 종횡비 언급 유무를 본다.
  artifact의 `promptVersion`이 `image-planner-v2`인지로 새 프롬프트가 실제로
  쓰였는지 확인한다.

- 대상: `prompts/` 아님. 생성 워커가 제출 직전에 합치는 네거티브 블록

- 기준 초안: `019ffa17-b48c-76be-8f25-8dfa48b397e2` 컷 0 (미러 셀카)

### 발단

운영자 가설: **제약이 과해서 모델이 자연스러움을 잃는 것 아닌가.** 다 지키려다
보니 부자연스러워진다.

### 실측 — 프롬프트 구성

| | 컷 0 | 컷 1 |
|---|---|---|
| Agent가 만든 프롬프트 | 1,968자 | 1,817자 |
| 워커가 뒤에 붙이는 네거티브 | **1,102자** | **1,102자** |
| fal.ai 전송 총량 | 3,070자 | 2,919자 |

전송본의 **36%가 네거티브**이고 두 컷이 완전히 동일하다 — 컷별로 다르지 않다.
금지어는 **62개**다.

결정적인 관찰: 우리가 실제로 관측한 결함 다섯 개(`extreme pinched waist`,
`overlong legs`, `unrealistic anatomy`, `plastic skin`, `deformed hands`)가
**전부 그 금지 목록에 이름 그대로 있다.**

### 가설

1. **부정 소환** — nano-banana는 `negative_prompt` 필드를 지원하지 않아
   (`falSupportsNegativePrompt`가 sd/sdxl/sd3만 true) 62개가 **긍정 텍스트로**
   프롬프트 끝에 붙는다. 부정 처리가 약한 모델에서 개념을 언급하면 오히려
   불러온다. 즉 금지한 결함을 유도하고 있을 수 있다.
2. **주의 예산** — 요구사항이 많으면 모델이 일부를 떨어뜨리고, 무엇을 떨어뜨릴지
   우리가 정할 수 없다.

### 방법

같은 레퍼런스 2장, 같은 모델, 4:5, 후보 2장. **프롬프트만** 다르게 한다.

- 조건 A = 현행 (3,070자)
- 조건 B = 워커 네거티브 1,102자만 제거 (1,968자)

Agent 프롬프트 끝의 짧은 부정(`no text, watermark, logo, …`)은 **남겼다** —
변수를 하나로 유지하기 위해서다.

### 파일럿 (조건당 2장) — 본실험에서 뒤집힘

| 관찰 축 | A (현행) | B (네거티브 제거) |
|---|---|---|
| 거울 가장자리 (계약 요구) | 선택본에 **없음** | 후보 0에 뚜렷하게 있음 |
| 허리-골반 전환 | 급격 | 완만 |
| 접지 그림자 | 거의 없음 | 있음 |
| 세팅 요소 충족 | 부분 | 신발장·소품·단차까지 |
| 로고 위반 | 후보 0에 New Balance | 없음 |
| 옷 주름 | 없음 | **없음 (변화 없음)** |

로고 항목이 특히 시사적이다 — `logo` 금지어를 **뺐는데도** 위반이 사라졌다.
1,102자가 로고를 막고 있던 것이 아니었다.

**gpt-image-2에서도 같은 방향이 관측됐다** (운영자 실행). 조건 A 결과는 다리
비율이 자연 범위를 넘었고, 조건 B 결과는 완화됐다. 서로 다른 두 모델이 같은
방향으로 움직였다는 점이 단일 모델 관측보다 강하다.

### 본실험 (시드 페어링 6쌍, 블라인드)

시드 대조($0.20)로 **시드 간 분산 ≫ 시드 내 분산**을 먼저 확인했다(같은 시드
2회는 근사 재현, 다른 시드는 구도·거울 위치까지 통째로 달라진다). 이어 시드
6개 × A/B 각 1장 = 12장을 생성하고, 좌우 배치를 무작위화한 뒤 판정자(운영자)
에게 쌍별 강제 선택 — "어느 쪽이 더 자연스러운 사진인가" — 만 물었다. 매핑
파일은 채점이 끝날 때까지 열지 않았다.

사전 등록 판정 규칙: 채택 = B가 5/6 이상이고 이진 체크 열세 없음. 기각 = B가
3/6 이하이거나 이진 체크에서 B가 명확히 나쁨.

| 쌍 | 시드 | 선택 | 조건 |
|---|---|---|---|
| 1 | 505 | 가 | **A** |
| 2 | 404 | 나 | **A** |
| 3 | 202 | 나 | **A** |
| 4 | 101 | 나 | **A** |
| 5 | 303 | 나 | B |
| 6 | 606 | 가 | B |

**A(현행) 4/6, B(제거) 2/6.** 이진 체크의 유일한 실패 — New Balance 로고 —
도 **B에서** 나왔다(p2-가). 기각 조건 두 개가 모두 충족됐다.

### 판정

**기각. 현행 유지.** `falSupportsNegativePrompt` 기반 코드 변경 후보는 철회한다.

파일럿이 속인 이유: 파일럿의 A는 파이프라인 산출물(시드 미상), B는 별도
호출이었다. 조건 차이가 아니라 **시드 차이**를 보고 있었고, 시드 간 분산이
워낙 커서 아무 두 장이나 집으면 다섯 축쯤은 한 방향으로 정렬된다. 파일럿 표의
"로고 위반: B에 없음"도 본실험에서 정반대로 뒤집혔다.

### 운영자 정정 — 장면 정합성은 자연스러움의 일부다

판정 직후 기록자(Claude)가 쌍 1의 탈락 사유(거울 반사가 아님, 실내에서 신발
착용)를 "네거티브 블록과 직접 관계없는 장면 정합성 문제"로 한정하려 했고,
운영자가 이를 바로잡았다. 두 겹으로 틀렸다.

1. **측정 정의**: 사전 등록한 질문이 "어느 쪽이 더 자연스러운 사진인가"였고,
   보는 사람이 겪는 자연스러움에는 장면 정합성이 포함된다. 결과를 본 뒤 측정
   범위를 질감·체형으로 좁히는 것은 사전 등록이 막으려던 바로 그 행동이다.
2. **사실관계**: 제거한 1,102자 안에 그 결함들의 방어 항목이 이름 그대로 있다 —
   `impossible mirror reflection`, `duplicated mirror`, `layout changes`,
   그리고 장소 네거티브의 `shoes`. 즉 쌍 1에서 B가 낸 결함은 네거티브 블록과
   무관한 것이 아니라, **그 블록이 막고 있던 것이 풀린 결과**와 텍스트로
   대응한다. 파일럿에서 "생활감 개선"으로 읽었던 신발장 위 신발·소품도 같은
   해석이 가능하다 — 장소 네거티브의 `shoes` 방어가 풀린 계약 위반일 수 있다.

결론적으로 네거티브 블록은 **장면 정합성 축에서 실제로 일하고 있었다.**

### 재리뷰 — 게시 가능 기준 (운영자, 판정 직후)

운영자가 같은 기준(장면 정합성 포함)으로 다시 보면 **쌍 2·4·5·6은 양쪽 다
선택할 것이 없다** — 즉 강제 선택 6개 중 4개는 "덜 나쁜 쪽" 지목이었지 게시
가능한 이미지 선택이 아니었다.

이 기준으로 다시 읽으면:

- **선택 가능한 이미지가 존재한 쌍은 1·3뿐이고, 둘 다 A가 이겼다.** B는 게시
  가능한 이미지가 있는 쌍에서 0승이다. 기각 판정은 더 단단해진다.
- **진짜 헤드라인은 통과율이다.** 12장 중 게시 가능 2~3장(쌍1-가, 쌍3-나 확정,
  쌍3-가 미확인). 현행 파이프라인(A)도 쌍 2·4·5·6에서 전부 탈락했다 — 묶인
  제약은 네거티브 블록이 아니라 장면 정합성이다.
- 공통 탈락 사유: **배경 현관이 실제와 동떨어지게 생성됨**(비현실적 재구성),
  **실내(마루)에서 운동화 착용**.

### 근본 원인 — 위반은 프롬프트가 상류에서 지시했다

두 조건이 공유한 Agent 프롬프트(컷 0)에 그대로 있다:

```
… stands on the oak floor about 1.3 meters from the full-length wall mirror …
She wears … and gray running shoes, all fully visible.
```

한국 주거에서 신발은 현관 타일까지다. 마루 위 + 운동화 "전부 보이게"는
문화적으로 성립하지 않는 장면인데, 기획→프롬프트가 그것을 **지시**했고 12장
전부가 물려받았다. 모델이 지시를 충실히 따를수록 위반이 선명해지고, 채택된
소수 이미지는 위반이 화면에서 두드러지지 않은 경우다.

같은 플래너가 항상 틀리는 것도 아니다 — 앞 초안(`019ff9b5…`)의 기획은 같은
장면에서 **"흰 양말"**이었다. 초안에 따라 맞기도 틀리기도 한다.

어느 평가 차원도 이것을 소유하지 않는다. `capture_plausibility`는 물리를,
`character_visual_grounding`은 외모·의상 경계를 소유하고, 주거 문화 규범은
어디에도 없다. **계약 안에 있는 결함은 아무도 잡지 않는다** — 평가자들은 계약
충실도를 재기 때문이다.

### 다음 실험 프로토콜 수정

강제 선택만 쓰면 절대 품질이 숨는다. 다음부터는 이미지별 **"게시 가능한가"
이진 게이트를 먼저** 통과시키고, 통과분끼리만 강제 선택한다. 통과율 자체가
제품 지표다.

기록자 한계(4번째 정정): 내 이진 체크는 12장 전부를 계약 충족으로 매겼다.
요소가 **있는지**를 확인했지 공간이 **현실적인지**를 확인하지 않았다 —
presence ≠ realism.

### 부수 발견 — 모델 성향과 계약 모순

레퍼런스 원본과 대조한 결과, 두 모델이 장소 레퍼런스를 반대로 다룬다.

- **gpt-image-2**: 레퍼런스를 거의 그대로 재현한다. 카메라 위치·시선·요소 배치가
  일치한다. 사실상 레퍼런스 사진에 인물을 합성한 그림이다.
- **nano-banana**: 재구성한다. 카메라를 옮기고, 거울을 반대쪽으로 옮기고, 없던
  소품을 만든다.

이는 **계약 자체가 모순이기 때문**이다. 같은 프롬프트가 두 카메라를 요구한다.

```
Use Image 2 for the cream entryway layout, right-side full-length mirror, …
… stands about 1.3 meters from the full-length wall mirror, aiming the lens
  squarely at the reflective surface
```

앞은 레퍼런스의 시점을, 뒤는 거울 앞 1.3m에서의 **좌우 반전된 반사상**을
요구한다. 한 이미지가 둘 다 만족할 수 없다.

| | 택한 쪽 | 얻는 것 | 잃는 것 |
|---|---|---|---|
| gpt-image-2 | 레이아웃 | `location_contract`, 장소 연속성 | 반사가 아닌 직촬 → 미러 셀카 불성립 |
| nano-banana | 촬영 | `capture_plausibility` | 장소가 매번 달라짐 |

이는 컷 1의 "폰을 신발장에 놓고 찍는다 + 그 신발장이 뒤에 보인다"와 **같은
유형**이다 — 모순된 계약을 주면 모델이 무엇을 버릴지 선택하고, 그 선택은 우리가
통제하지 못한다. `image-planner-v2` 판정의 "원칙 일반화 미달"이 컷 안이 아니라
레퍼런스 바인딩과 촬영 지시 **사이**에서도 확인된다.

개선 후보(미적용): 미러 셀카 컷의 `preserve`는 "layout"이 아니라 **요소**를
보존해야 한다. 가구 구성·색·재질은 고정하되 카메라 위치와 좌우는 촬영 지시가
소유한다. `image-planner-v3` 후보지만, `image-planner-v2` 관측이 진행 중이므로
지금 바꾸면 측정이 섞인다.

### 실험 설계 (사전 등록, 2026-08-14)

**본 생성 전에 확정한다.** 이미지를 본 뒤에 기준을 정하면 사전 등록이 아니다.

**편향 고지**: 파일럿 4장(A 2, B 2)은 이미 봤다. 아래 설계는 **새로 생성할
표본**에 대한 사전 등록이며, 파일럿은 판정 집계에 넣지 않는다.

#### 조건

| | 프롬프트 |
|---|---|
| A | Agent 프롬프트 + 워커 네거티브 1,102자 (현행, 3,070자) |
| B | Agent 프롬프트만 (1,968자) |

고정: 모델 `fal-ai/nano-banana-pro/edit`, 레퍼런스 2장과 순서, `aspect_ratio 4:5`,
기준 초안 `019ffa17…` 컷 0. **변수는 프롬프트 하나뿐이다.**

A도 파이프라인 산출물을 재사용하지 않고 B와 **같은 직접 호출 경로**로 새로
생성한다. 워커 경로와 curl 경로의 차이를 변수에서 제거하기 위해서다.

#### 표본

시드 지원 여부를 먼저 확인한다(같은 시드·프롬프트로 2회 호출해 동일 출력인지).

- **지원**: 시드 6개 × 2조건 × 1장 = 12장. 같은 시드끼리 짝지어 시드 분산을 제거
- **미지원**: 조건당 8장 = 16장

#### 판정 도구 1 — 일반 사진 무결성 (계약 무관, 재사용 가능)

| | 체크 |
|---|---|
| G1 | 발밑에 접촉 그림자가 있는가 |
| G2 | 손가락 개수와 형태가 정상인가 |
| G3 | 프레임에 텍스트·로고가 **없는가** |
| G4 | 반사면이 있다면 반사 내용이 실제와 정합하는가 |

**의도적으로 뺀 것**: "굽은 관절에 옷이 접히는가". 레깅스는 신축 원단이라 접히지
않고 늘어나므로 이 의상에 맞지 않고, "충분한가"가 정도의 문제라 이진화되지
않는다. 원근·조명 방향도 같은 이유로 뺐다.

#### 판정 도구 2 — 계약 파생 (이번 컷 전용, 프롬프트에서 기계 추출)

프롬프트의 `Include …` 절과 의상·인물 지시에서 그대로 뽑았다.

| | 체크 |
|---|---|

판정자(운영자) 게이트 결과. "선택"은 강제 선택이 아니라 **그 쌍에서 유일하게
게시 가능했던 쪽**이다 — 둘 다 통과한 쌍이 0개라 강제 선택은 발생하지 않았다.

| 쌍 | 시드 | 가 | 나 | 게이트 |
|---|---|---|---|---|

| 3 | 703 | C | A | 나(A)만 O |

  그 시드의 결함은 그대로였다

### 판정

**기각.** 사전 등록 규칙(C 통과가 A 이하면 기각)에 걸린다. 단언 예산 가설은
이 표본에서 지지되지 않는다.

뉘앙스: 악화도 아니다. 727자(24%)를 빼도 통과율·생존 패턴이 동일했다 — 비용
없는 축약이지만 개선 근거도 없다. planner-v3를 "단언 예산" 원칙으로 재설계할
근거는 사라졌다.

### 이 실험 쌍이 함께 말하는 것

운영자의 과제약 가설 양 절반이 모두 검증됐다 — 네거티브 제거(B)는 **악화**,
긍정 단언 축약(C)은 **무효과**. 즉 이 파이프라인에서 **프롬프트 길이 층은
통과율의 지렛대가 아니다.** 통과율(이번 33%, 앞 라운드 17~25%)을 지배하는 것은
시드가 끌고 오는 장면 구성이고, 같은 시드 안에서 프롬프트를 ±36% 바꿔도 생사가
거의 갈리지 않았다.

남는 지렛대 후보 (관측 근거 순):

1. **컷당 후보 수 확대 + 게이트** — 시드 분산이 지배하므로 best-of-N이 가장
   직접적인 대응. 단, 게이트를 사람이 서면 검수 비용이 N배가 된다. 평가
   Agent는 자연스러움 축에서 눈이 멀어 자동 게이트로 부적합(§18.8)
2. **계약 모순 수정(R1·R2)** — 어블레이션과 무관하게 기획 관측에서 성립한
   결함(지지 가구 프레임 침입, layout↔반사 시점). 통과율 개선 폭은 미지수
3. **모델 비교** — 계약을 고친 뒤에 재는 것이 유효 (앞서 합의한 순서)

### 기록자 오류 (5번째)

판정 완료 전 통과 산수를 잘못 계산해("답에 따라 A2:C4가 될 수 있다") 불필요한
확인 질문을 했다. 미확정 4장은 A2·C2 대칭이라 어느 응답이어도 동률 → 기각으로
동일했다. 확인 질문 자체는 판정 모호성을 없앴으므로 무해했지만, 근거가 틀렸다.

## post-planner-v2 / caption-writer-v1 / post-evaluator-v2 — 캡션 소유권 이동 (2026-08-15)

### 가설

캡션이 부자연스러운 원인 중 **구조적인 것**은 두 가지다.

1. 캡션이 이미지보다 먼저 쓰인다. 사람은 찍고, 보고, 쓴다. 먼저 쓰면 사진과
   어긋나도(§18.3의 "거울 앞에 한 번 더 서게 돼요" ↔ 성립하지 않는 거울 시점)
   사람 눈에 걸릴 때까지 살아남는다.
2. 게시글 기획 프롬프트가 11개 차원어치 책임을 지느라 캡션 예시에 쓸 지면이
   없다. 전용 Agent라야 페르소나 예시와 운영자 정정 사례를 few-shot으로 넣을
   자리가 생긴다(§18.7).

한국어 연어 자연스러움 자체를 LLM이 판정하게 만들지는 **않는다** — 그 축에서
평가자가 무능한 것은 관측된 사실이다(§18.8, 캡션에 `ai_tell_free 5/5`).

### 변경

**post-planner-v2** (`post-plan-v2`): 출력에서 `caption`·`captionLanguages`·
`hashtags` 삭제. 남는 것은 `intent`(premise/purpose)·`newMemoryCandidates`·
`conflicts`. Mission 문장을 "캡션은 뒤에서 다른 Agent가 이미지를 보고 쓴다"로
바꾸고, premise에 다음 요구를 추가했다:

```
State the premise concretely enough that a caption written later from it alone
cannot invent a new event, place, or relationship.
```

**caption-writer-v1** (`caption-set-v1`, 신규): 입력은 intent + writing profile
+ recentPosts + operatorRequest + **컷별 ImagePlan 원문**(visualPurpose/scene/
lockedElements) + **생성 이미지**(vision) + 선택적 operatorNote. 핵심 규칙:

```
Mention a visible element only if it appears in the generated image AND in that
shot's image plan text. An element visible only in the image (an unplanned
object) may be a generation defect — do not promote it into the post. An element
present only in the plan (a generation omission) is not in the photo — do not
describe it.
```

양방향인 이유: 이미지에만 있는 것을 쓰면 **생성 결함이 게시물의 사실로 승격**
되고(R1의 "신발장 위 폰"이 그대로 캡션이 될 수 있었다), 계획에만 있는 것을 쓰면
**사진에 없는 것을 말하는 캡션**이 된다. 해시태그 규칙(프로필·반복 사용·호환
요청만, 새 장소·루틴·브랜드 태그 금지)은 post-planner-v1에서 그대로 이관했다.

**post-evaluator-v2**: 글 4차원(`voice_fit`·`ai_tell_free`·`caption_quality`·
`hashtag_fit`)을 **삭제**했다. 이동이 아니라 삭제다 — 평가 대상(캡션)이 이
Agent의 입력에서 사라졌고, 캡션 평가 Agent는 만들지 않는다. `memory_discipline`
과 `scope_compliance` 문구에서도 caption 참조를 걷어냈다. 11차원 → 7차원.

### 관측 방법 (배포 후)

지표는 인프라 신설 없이 기존 데이터에서 유도한다(아키텍처 §20.8).

- **개입률 3분리**: 편집(`captionBuild.output.caption` ≠ `Post.content`) /
  `operatorNote` 사용 / ⑥ 재실행 >1회. 셋을 합치면 "note로 3번 조종한 뒤 무편집
  승인"이 개선으로 보인다.
- **편집 유형 라벨**: 연어 / 이미지-픽셀 어긋남 / 계획 밖 요소 / 페르소나 /
  반복 / 기타. 라벨 규칙은 첫 쌍을 열기 **전에** 여기 등록하고, 1차 라벨은 편집
  당사자가 `DRAFT_CAPTION_EDITED` reason에 남긴다(라벨러 = 프롬프트 변경 결정자
  편향 완화 — `detail-budget-ablation`에서 사후 범위 축소 전례).
- 표본 수를 항상 함께 적는다. n=1로 판정하지 않는다.

### 위험

- **V4-1 단독으로 연어가 개선된다는 근거는 없다.** 여는 것은 (a) 이미지 근거,
  (b) few-shot 지면 두 가지이고, few-shot 주입은 정정 쌍이 쌓인 뒤(V4-3)다.
  이 단계에서 캡션이 나아지지 않아도 기각이 아니라 "아직 관측 전"이다.
- 자동 모드는 사람이 보지 않고 게시된다(검수 삭제). 자동 게시물의 사후 수정·
  삭제 건수를 함께 세지 않으면 품질 저하가 지표에 안 잡힌다.
- ③ 입력에서 caption이 빠지므로 `image-planner-v3` 관측 조건이 바뀐다. 프롬프트
  문장·버전은 불변이므로, 이후 v3 결함은 "톤 힌트 없는 입력" 조건에서 난 것으로
  읽어야 한다(위 예고 항목).
